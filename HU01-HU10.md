# Latia — entrega HU01–HU10

Esta entrega completa el CRUD de usuarios y perfiles de salud de las diez tarjetas del Sprint 1. La carpeta duplicada `Latia_Lati/` sigue eliminada. Las otras historias y los demás hallazgos de la auditoría no se consideran resueltos por esta entrega.

## Abrir y ejecutar

1. Extraer el ZIP en una carpeta nueva y abrir el `pom.xml` de `Latia/` en IntelliJ.
2. Seleccionar JDK 21 para el proyecto y para Maven. Recargar Maven.
3. Conservar/configurar la conexión a la base PostgreSQL local en el entorno de desarrollo. No ejecutar con datos de producción.
4. Ejecutar `mvnw.cmd test` en Windows, o `bash mvnw test` en Linux/macOS. Las pruebas usan H2 en memoria con el perfil `test`; no usan la base PostgreSQL personal.
5. Ejecutar `mvnw.cmd spring-boot:run` o la clase `LatiaLatiApplication`.
6. Registrar una cuenta y volver a iniciar sesión. Los JWT anteriores no contienen `userId` y no son válidos para los módulos corregidos.
7. Abrir `http://localhost:8080/swagger-ui/index.html`, iniciar sesión en `POST /login` y usar el token en Authorize.

La configuración local y los secretos originales de `application.properties` no se rotaron. Tampoco se sustituyeron los secretos de su historial Git. Antes de publicar se debe resolver ese punto de la auditoría, junto con la autorización de los demás módulos.

## Contrato implementado

| HU | Método y ruta | Acceso | Respuesta correcta |
|---|---|---|---|
| HU01 | POST `/api/users` | Público | 201, DTO y Location |
| HU02 | GET `/api/users` | Administrador | 200, lista de DTOs |
| HU03 | GET `/api/users/{id}` | Cuenta propia o administrador | 200, DTO |
| HU04 | PUT `/api/users/{id}` | Cuenta propia o administrador | 200, DTO actualizado |
| HU05 | DELETE `/api/users/{id}` | Cuenta propia o administrador | 204, sin cuerpo |
| HU06 | POST `/api/healthprofiles` | Usuario autenticado, propietario del perfil | 201, DTO y Location |
| HU07 | GET `/api/healthprofiles` | Solo perfiles del propietario autenticado | 200, lista de DTOs |
| HU08 | GET `/api/healthprofiles/{id}` | Propietario | 200, DTO |
| HU09 | PUT `/api/healthprofiles/{id}` | Propietario | 200, DTO actualizado |
| HU10 | DELETE `/api/healthprofiles/{id}` | Propietario | 204, sin cuerpo |

Los listados vacíos devuelven 404 con mensaje, según las tarjetas HU02 y HU07. El caso vacío del directorio de usuarios es normalmente inalcanzable en HTTP porque el administrador activo también pertenece a la lista.

Los IDs de ruta deben ser positivos. Se devuelve 400 por datos inválidos, 401 por falta de autenticación/sesión no vigente, 403 por operaciones no autorizadas, 404 por recursos inexistentes y 409 por duplicados o dependencias que impiden borrar. En perfiles, un recurso ajeno también devuelve 404 para no confirmar que existe. En usuarios, un usuario normal recibe 403 al intentar gestionar cualquier otra cuenta; un administrador puede comprobar el 404 de un ID inexistente.

## Decisiones de permisos

- Todas las cuentas nuevas reciben `ROLE_USER` en el servidor. No hay un registro público de administradores.
- El administrador de cuentas puede listar y gestionar cuentas; no obtiene acceso automático a historias o perfiles médicos ajenos.
- Para probar HU02, un responsable del entorno debe asignar `ROLE_ADMIN` a una cuenta de prueba mediante la administración de su BD. Las pruebas automatizadas crean ese rol únicamente en la BD de pruebas. No se incluyen usuarios administrativos ni contraseñas universales.
- El propietario de un perfil se obtiene del JWT. `idOwnerUser` es opcional; si se envía debe coincidir con el usuario autenticado.
- `idHolderUser` puede ser null para un dependiente o el propio ID para el perfil personal. Vincular cuentas ajenas queda bloqueado hasta implementar consentimiento/invitaciones. Los enlaces previos a titulares ajenos no se migran silenciosamente y requieren revisión antes de editarlos.
- Cambiar el propietario mediante PUT está prohibido. La relación de parentesco no concede permisos por sí sola.
- Las cuentas desactivadas o eliminadas se rechazan al acceder a estos módulos, incluso con un JWT emitido anteriormente. Los permisos administrativos se consultan en la BD para que retirar un rol tenga efecto inmediato en estas operaciones.

## JSON de ejemplo

Registrar una cuenta:

```json
{
  "firstName": "Ana",
  "lastName": "Prueba",
  "username": "ana.prueba",
  "email": "ana.prueba@example.test",
  "password": "Cambiar.Ejemplo123!"
}
```

`passwordHash` sigue aceptándose como alias de `password` solo en el registro, por compatibilidad con las solicitudes anteriores. Siempre se trata como contraseña de entrada y se cifra en el servidor. El DTO de salida no incluye contraseña, hash ni roles. Los IDs, fechas, estado y roles que se envíen como propiedades adicionales del registro no controlan los valores persistidos.

Actualizar datos con `PUT /api/users/{id}`:

```json
{
  "firstName": "Ana María",
  "lastName": "Prueba",
  "username": "ana.prueba",
  "email": "ana.prueba@example.test"
}
```

El ID autoritativo es el de la URL. Este PUT no modifica contraseña, roles, estado ni fechas de creación. Si cambia el username, se debe iniciar sesión otra vez con el nuevo nombre. Los timestamps de usuarios se devuelven como `LocalDate` (`AAAA-MM-DD`), coherentes con la entidad y la BD existentes; no se inventa una hora de auditoría.

Cambiar contraseña en la cuenta propia con `PUT /api/users/{id}/password`:

```json
{
  "currentPassword": "Cambiar.Ejemplo123!",
  "newPassword": "Otro.Ejemplo456!"
}
```

Se exige la contraseña actual y una nueva de al menos 8 caracteres y hasta 72 bytes UTF-8 por el uso de BCrypt. Este cambio no implementa una lista de revocación de todos los JWT ya emitidos. Esa política global de sesiones queda pendiente.

Crear o actualizar un perfil:

```json
{
  "firstName": "Lucía",
  "lastName": "Prueba",
  "idHolderUser": null,
  "birthDate": "2015-03-10",
  "sex": "Femenino",
  "bloodType": "O+",
  "phone": "+51 999999999",
  "active": true
}
```

`firstName` y `lastName` identifican al paciente, no al dueño de la cuenta. El nombre y apellido se añadieron como columnas opcionales en la BD para permitir perfiles históricos existentes, pero son obligatorios en nuevas solicitudes de alta/edición. Con `ddl-auto=update`, Hibernate incorpora las columnas; revisar primero una copia de la BD existente. Los perfiles históricos no reciben nombres inventados: se deben completar con información real al editarlos.

El grupo sanguíneo admite A+, A-, B+, B-, AB+, AB-, O+ y O-. Esto mantiene el dato obligatorio de su DTO previo; si la HU necesita admitir un grupo desconocido, acordar y ampliar el contrato antes de usarlo con personas reales.

## Eliminaciones y transacciones

Se elimina físicamente cuando no hay datos dependientes que lo impidan. Si existen perfiles vinculados a una cuenta, o documentos/contactos/historias vinculados a un perfil, la operación puede devolver 409 y se revierte entera. No se añade borrado en cascada de información clínica. Eliminar una cuenta sí conserva la cascada previa sobre sus propios roles.

Esto explicita el caso no descrito en las tarjetas: no se afirma que siempre se pueda borrar un registro con dependencias. Si el profesor exige otro comportamiento, hay que definirlo con el grupo.

## Arquitectura y cambios de integración

- Controllers: HTTP, DTO validado, URI y código de respuesta.
- Servicios: permisos, existencia, reglas, mapeos y transacciones.
- Repositories: consultas JPA y restricciones de persistencia.
- Mapeos explícitos para usuarios y perfiles; no dependen de ModelMapper STRICT.
- Bean Validation declarado en Maven y aplicado tanto en entrada HTTP como en servicios.
- Errores de autenticación de los controllers, permisos, validaciones y conflictos incorporados al handler existente.
- `Users.passwordHash` y `Role.user` excluidos de serialización como defensa adicional.
- `IHealthProfileService.listId()` se conserva para los otros módulos, pero ahora solo devuelve perfiles del propietario. Eso protege las operaciones que lo utilizan; no equivale a haber auditado o corregido todos los endpoints de documentos, tratamientos y registros clínicos.
- Los antiguos `PUT /api/users` y `PUT /api/healthprofiles` se sustituyen por rutas `/{id}`. Actualizar solicitudes de Swagger, Postman o frontend.
- Todos los DTOs mantienen clases convencionales (`class`), campos privados, constructor vacío, constructor con parámetros, getters y setters, siguiendo el estilo del proyecto original. Dentro de Java se usa `getIdUser()`, etc. No hay declaraciones `record` en el proyecto. El contrato JSON se conserva.
